How the storage works

Think of the dynamic table as a small ordered notebook of header fields. Two hash maps help find a name or a name/value pair; a FIFO chain says which field leaves first. Bucket arrays are internal lookup storage, not network buffers and not the HPACK byte budget.

Growth copies the notebook, not the output buffer

The original side shows the baseline mask; stage 3 uses a short mask even before growth. Both bucket arrays remain final: their references never change within an encoder. New nodes prevent copying from relinking the original encoder. Header name/value objects may still be referenced by both encoders; this is not a deep copy of all strings. Pending minimum table-size updates, configured limits and protocol occupancy are carried over. A no-growth setting returns the same encoder. Shrinking evicts entries as necessary, but retains bucket capacity.

Decide whether to admit before making room

16 is an admission bound, not a universal chain-length invariant. At a large table, an insertion must not extend the pair bucket past 16. A static-table name or already-present name does not extend the name chain, but the pair check still applies. A genuinely new name needs space in its name bucket too. Existing exact-pair hits do not insert at all.

128 is inherited small-table occupancy, not a newly introduced chain limit. A 4096-byte HPACK table has at most 128 entries under the minimum 32-byte entry accounting. Small tables retain their old behavior. Chains longer than 16 can therefore survive growth; they are preserved and drain with eviction, rather than being rewritten or silently dropped. Larger bucket arrays can spread some chains but do not eliminate equal-hash collisions.

Entry counters are labels, not popularity counts

An entry's counter identifies its position relative to the newest insertion. Reading a header repeatedly does not increment a usage count. The existing formula computes a dynamic-table index from counter − latestCounter + 1; the static-table offset is added for the wire index. A name entry points at the label of the newest matching name, so removing an older pair must not remove a still-useful name mapping. Stage 3 copies these labels; it does not invent this scheme.

Advanced: inherited integer wraparound behavior

Insertion labels decrease. The existing subtraction-based indexing also works across signed integer wraparound while the live window is bounded. Growth must preserve labels and ordering, not renumber nodes. The new tests exercise that inherited behavior; overflow is not the motivation for this series and is not a new counter feature.

What this does not claim

  • 64 KiB is protocol accounting, not Java heap. HPACK counts name length + value length + 32 per entry. Arrays, node objects, strings, headers, buffers and object overhead are additional heap costs. Readiness retention is not a retained-heap measurement.
  • Cold configuration has an allocation peak. Growth allocates a replacement encoder, larger arrays and replacement nodes while the old encoder still exists. It preserves the old structure if construction fails, but does not make SETTINGS free. Shrink does not shrink arrays. Steady-state timings alone do not measure this peak; the current 4 KiB initialization cell does not measure populated 64 KiB growth.
  • Raw hashing remains. There is no mixed-hash redesign in this series. Bounded admission can starve available capacity under skewed buckets. The prior diagnostic warning of roughly 45 KiB retained after about eight thousand fields must not be treated as a new-series measured result or a universal threshold; retain it as a limitation to investigate with the exact fixture/proof. Near-64 KiB retention in one proven fixture does not guarantee every workload fills the table.
  • Eager Huffman construction is unchanged. The per-encoder Huffman object remains eagerly constructed, including in replacement encoders. This series does not claim to fix its allocation cost.
  • Synthetic is not a production trace. Repeated, churn, collision and working-set cases isolate mechanisms. Browser-shaped fixtures are also controlled workloads, not captured real browsing traces. See exact selectors and parameters in the evidence section.
  • Shared-host confidence intervals are not parity. Pairing helps account for round effects, but contention, scheduling and systematic bias remain. Six primary pairs (including initialization) or three capacity pairs are limited evidence. Intervals are not multiplicity-adjusted. A CI spanning zero is uncertainty, not proof of equivalent performance.
  • Ordinary 4 KiB measurements do not establish parity. All 90 primary timing intervals cross zero in the completed campaign. Preserving the default allocation shape and bypassing large-table admission is a design choice, not a measured zero-cost guarantee.
  • No false upstream 64 KiB comparison. Only stage 3 supports the requested 64 KiB encoder table. Capacity charts compare stage 3 against itself at 4 KiB; they do not compare a real 64 KiB encoder against an upstream encoder silently clamped to 4 KiB.
